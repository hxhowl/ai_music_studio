# 记录什么、记在哪

> 两类记录，**必须分开**。混在一起会出现两种误导：
> 把某一首歌的临时偏好当成项目规则；或者反过来，把项目级的教训埋进某首歌的文件夹里，下次再也找不到。

| | A · 工程迭代记录 | B · 单首歌创作记录 |
| --- | --- | --- |
| 记什么 | 规则为什么改成这样、踩过什么坑、用户对**流程/产品**的偏好 | 这一首歌怎么一步步改出来的 |
| 放哪 | `.workbuddy/memory/` | `outputs/{歌曲名}/{歌曲名}-log.md` |
| 读者 | 下一个会话的 AI | 下一次迭代（要追溯"当时为什么这么改"） |
| 生命周期 | 长期，可跨歌 | 跟着这首歌 |

**分界判据**：**换个歌名还成立吗？**
成立 → 记进 A（工程）；不成立 → 记进 B（那首歌）。

---

## A · 工程迭代记录

- **工作日志**：`.workbuddy/memory/YYYY-MM-DD.md`（**追加写，不覆盖**）
- **长期约定**：`.workbuddy/memory/MEMORY.md`（策展后的结论，不是流水）
- **值得写**：规则为什么这么定（以及为什么推翻过）、哪次实测暴露了什么、用户对流程/产品的稳定偏好、平台规范的新发现
- **不写**：单首歌的创作过程、临时搜索结果、生成结果全文

⚠️ 判据是"**换个歌名还成立**"。写之前先问一遍，否则会把单次偏好固化成规则。

## B · 单首歌的创作记录

文件：`outputs/{歌曲名}/{歌曲名}-log.md`（**追加写、不覆盖、不带版本号**）

### 记什么

每轮两行（用户 + AI），**全文不超过用户原话本身的长度**：

```markdown
## YYYY-MM-DD

- **用户**：<原话，完整>
- **AI**：<改了什么，一行> → `-lyrics-vN-YYYYMMDD.md`
```

**用户的话照抄，不改写、不概括、不删减。**
理由：日志的全部价值是保真。一句"他说主歌不好"和原话"主歌像流水账，六个物件堆在一起，
没有一个动作连起来"——后者才能让人知道下次该防什么，前者什么也没说。
用户发言一般不长，全文照录的成本很低。

> 唯一例外：用户贴进来一大段素材/参考歌词（超过 10 行）时，
> 写「（贴了一段素材，约 20 行，见他当时的消息）」即可，不要把素材抄进日志。

### 不写

| ❌ | 为什么 |
| --- | --- |
| 思考过程、分析、推理 | 那是过程，不是事实 |
| 完整歌词 | 版本文件里已有；抄一遍，两处就开始漂移 |
| 自检、逐条规则对照 | 不是交付内容，也不是事实 |
| **"他大概想要的是…"这类推测** | 推测一旦写进日志，下次会被当成用户说过的话来读 |
| 事后评价（"这一改其实是错的"） | 判断留给你，日志只记发生了什么 |

### 两条硬规矩

- ⚠️ **不要补记**。过去没留存就是没留存——靠产出反推、靠印象回忆拼出来的"日志"，
  是把推断写成事实，比空白更有害。缺哪段就空着，从下一次真实对话开始记。
- ⚠️ **不要贴进对话回复**。它是给下一次迭代看的，不是交付内容。

### 什么时候不记

用户只是闲聊、没产出文件时，可以不记。一轮 = 一次用户发言 + 一次回应；
**串行时只记一条**（一次发言里既出词又出提示词，AI 那行写「出词 v2 + 提示词 v2」）。

### 为什么不带版本号

版本文件是**快照**，日志是**一条线**。`log-v1` `log-v2` 每份都得含前面全部历史，只会重复三遍。
所以它刻意不参与版本号体系：一个文件，一直往后追加。

---

## 从 B 升到 A

某首歌里反复出现的偏好（第 2、3 次出现），才考虑升级成工程规则：

```
B 里出现过 2 次以上  →  调研是不是普遍规律  →  写进 A（MEMORY.md）→ 若涉及行为约束，才动 AGENTS
```

⚠️ **一次不算**。单次偏好升格成规则，正是这个项目规则膨胀的原因之一。
